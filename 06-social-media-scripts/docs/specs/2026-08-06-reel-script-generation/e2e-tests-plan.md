# E2E test plan — Reel Script Generation

Spec: `docs/specs/2026-08-06-reel-script-generation/`
Generated by `/plan-test-cases` · consumed by the `generate-tests` subagent

## Preconditions

- **App: `http://localhost:3001`** — **not** 3000. `playwright.config.ts` sets
  `baseURL` and `webServer.url` to 3001 with `reuseExistingServer: true`, so
  Playwright reuses the running dev server or starts one on that port. Use
  `page.goto('/')`, never a hard-coded origin.
- **Environment:** `.env.local` holds `IG_SESSIONID` and `OPENROUTER_API_KEY`.
  The app refuses to start a run without them (criterion 7.2), so they must be
  present even for the cases that intercept the network — the abort under test
  in Case 2 is simulated at the API boundary, not by unsetting a variable.
- **State:** the single route is `/`. The actor `<select>` is populated
  server-side from `profiles/`, which currently holds exactly one profile,
  `juanse`. No login, no seeded database, no cleanup between cases.

### External calls — read this before writing a single test

A real run calls Instagram and OpenRouter and takes **minutes**: it downloads
video, shells out to ffmpeg, transcribes, then makes two LLM calls per reel. It
also costs money and can fail for reasons that have nothing to do with this
code — a rate limit, a rotated cookie, a private account.

**All three cases therefore intercept the two API routes** with
`page.route()`, fulfilling them with fixtures that match the real contract:

- `POST /api/runs` → `201 { "runId": "<id>" }`
- `GET /api/runs/<id>` → a `RunView` object

That boundary is exactly where the design puts it: the page's whole job is to
start a run and render what the poll returns. The pipeline behind the route is
covered by 255 unit and workflow tests, including the per-step failure matrix.

**What this deliberately does not prove**, and what a human should smoke-test
once by hand: that a live run against a real account actually produces a script.
Automating that would make the loop slow, expensive and flaky.

## Case 1 — A completed run shows each reel's analysis and script (happy path)

- **Traces to:** 5.1, 5.2, 5.3, 5.4, 5.5
- **Objective:** starting a run from the form and polling to completion puts a
  usable, copyable script on screen for every successful reel.
- **Preconditions:** intercept both API routes. The first `GET` returns a
  `running` view, the second a `completed` one, so the poll transition is
  exercised rather than assumed.
- **Steps:**
  1. Intercept `POST /api/runs` → `201 { "runId": "run_e2e_1" }`.
  2. Intercept `GET /api/runs/run_e2e_1`. First call returns:
     ```json
     { "runId": "run_e2e_1", "account": "morningbrew", "actor": "juanse",
       "status": "running",
       "reels": [
         { "rank": 1, "shortcode": "r1", "thumbnailUrl": "", "metrics": { "views": 6900000, "likes": 412000, "comments": 1820 }, "status": "pending", "currentStep": "transcribe" },
         { "rank": 2, "shortcode": "r2", "thumbnailUrl": "", "metrics": { "views": 1200000, "likes": 88000, "comments": 430 }, "status": "pending", "currentStep": "download" }
       ] }
     ```
     Every later call returns the same object with `"status": "completed"` and
     both reels as
     `{ "status": "ok", "analysis": { "objective": "Reformular un dato conocido", "highlights": ["Abre con una contradicción", "Nombra un número duro"], "targetAudience": "Fundadores curiosos" }, "script": { "hook": "HOOK UNO", "body": "CUERPO UNO", "closing": "CIERRE UNO" } }`
     for rank 1 and the same shape with `HOOK DOS` / `CUERPO DOS` / `CIERRE DOS`
     for rank 2.
  3. `page.goto('/')`.
  4. Assert the actor `<select>` (label **"Actor"**) has exactly one option with
     value `juanse` — the profiles directory holds exactly that one (5.2).
  5. Fill the field labelled **"Cuenta"** with `morningbrew`.
  6. Leave **"Reels"** at its default value of `3`.
  7. Click the button **"Generar"**.
- **Expected result:**
  - The text `Run: run_e2e_1` appears — the id the route returned reached the
    page (5.1).
  - While the run is `running`, **`transcribe`** and **`download`** are both
    visible at the same time: the step is reported per reel, not per run (5.3).
  - After the poll returns `completed` (the page polls every 2 s; wait for the
    assertion, never `waitForTimeout`), the card `[data-testid="reel-1"]`
    contains the heading `#1`, the text `6900000 views`, `412000 likes`,
    `1820 comments`, the section headings **"Análisis"** and **"Script"**, the
    objective `Reformular un dato conocido`, both highlights, and the script's
    `HOOK UNO`, `CUERPO UNO` and `CIERRE UNO` (5.4).
  - `[data-testid="reel-2"]` likewise shows `HOOK DOS` (5.4).
  - Each `ok` card has exactly one button labelled **"Copiar script"**. Clicking
    the one inside `[data-testid="reel-1"]` changes its label to **"Copiado"**
    (5.5).
- **Notes:**
  - Grant clipboard permission before clicking:
    `context.grantPermissions(['clipboard-write'])` in Chromium. If the label
    does not flip to "Copiado", the copy promise rejected — that is a real
    finding, not a flake, and belongs in the report.
  - Assert on `[data-testid="reel-N"]` scopes, not on page-wide text: both cards
    carry the same headings, and a page-wide `getByText('Script')` matches twice.
  - Never assert on `Iniciando…`; it is only visible before the first poll
    resolves and racing it is what makes a test flaky.

## Case 2 — An expired Instagram cookie aborts the run and tells the operator what to do (failure path)

- **Traces to:** 7.3, and the same rendering path as 1.5, 4.5 and 7.2
- **Objective:** when a run aborts, the page stops polling and shows the
  operator-facing instruction verbatim instead of spinning forever.
- **Preconditions:** intercept both routes; the poll returns an `aborted` view
  from the first call.
- **Steps:**
  1. Intercept `POST /api/runs` → `201 { "runId": "run_e2e_2" }`.
  2. Intercept `GET /api/runs/run_e2e_2`, **counting the calls**, and always
     return:
     ```json
     { "runId": "run_e2e_2", "account": "morningbrew", "actor": "juanse",
       "status": "aborted",
       "error": { "code": "ig-session-expired",
                  "message": "Instagram rejected the request with HTTP 403 — the session cookie has expired. Rotate IG_SESSIONID with a fresh cookie from a disposable account." },
       "reels": [] }
     ```
  3. `page.goto('/')`, fill **"Cuenta"** with `morningbrew`, click **"Generar"**.
- **Expected result:**
  - An element with `role="alert"` contains the text
    `Rotate IG_SESSIONID with a fresh cookie from a disposable account.` — the
    rotate-the-cookie instruction reaches the screen (7.3).
  - No reel card is rendered: `[data-testid^="reel-"]` has count 0.
  - **Polling stops.** Record the intercept's call count once the alert is
    visible, wait past two poll intervals (~5 s), and assert the count has not
    grown. A terminal status that keeps polling is a real defect.
- **Notes:**
  - This same code path renders `account-not-found` (1.5), `unknown-actor` (4.5)
    and `missing-ig-session` (7.2); one case covers the rendering for all four,
    and the per-code mapping is unit-tested in `run-view.test.ts`.
  - The message must be asserted verbatim from the fixture, not with a loose
    `/rotate/i` — the point is that the operator gets the whole instruction.

## Case 3 — A reel that failed shows its reason, and the rest still deliver (failure path)

- **Traces to:** 5.6, 6.2, and the user-visible half of 6.1
- **Objective:** one broken reel does not cost the batch: the failed card shows
  why, carries no script to copy, and its siblings render normally.
- **Preconditions:** intercept both routes; the poll returns a `completed` view
  mixing two `ok` reels and one `failed`.
- **Steps:**
  1. Intercept `POST /api/runs` → `201 { "runId": "run_e2e_3" }`.
  2. Intercept `GET /api/runs/run_e2e_3` → `completed`, with reels:
     - rank 1 `ok` (analysis + script, `HOOK UNO` / `CUERPO UNO` / `CIERRE UNO`),
     - rank 2 `{ "status": "failed", "failedStep": "download", "reason": "video not available (404)" }`,
     - rank 3 `ok` (`HOOK TRES` / `CUERPO TRES` / `CIERRE TRES`).
     Return them **in ascending rank order** (1, 2, 3), because that is what the
     real API emits: the invariant is owned server-side and enforced at both
     producers — `assemble` (`src/mastra/workflows/generate-scripts.ts`) and
     `toRunView` (`app/api/runs/run-view.ts`), the latter unit-tested against an
     out-of-order input in `run-view.test.ts`. An earlier revision of this plan
     mandated a `3, 1, 2` payload and demanded the client re-sort it; that
     scenario cannot occur, and the resulting test failed against correct code.
  3. `page.goto('/')`, fill **"Cuenta"** with `morningbrew`, click **"Generar"**.
- **Expected result:**
  - Three cards render, and their `#rank` headings read `#1`, `#2`, `#3` in
    document order. Kept as a regression guard: against a contract-faithful
    payload it still catches a client change that shuffles or drops a card.
  - Inside `[data-testid="reel-2"]`: an element with `role="alert"` reads
    `video not available (404)` (5.6).
  - Inside `[data-testid="reel-2"]`: **no** "Copiar script" button, and neither
    "Análisis" nor "Script" appears — the reason stands *in place of* them, not
    beside them (5.6).
  - `[data-testid="reel-1"]` and `[data-testid="reel-3"]` each show their script
    text and one "Copiar script" button (6.2 — the successful reels are still
    delivered).
- **Notes:** the rank-2 metrics still render on the failed card; a failed reel
  keeps its identity. Assert one metric on it so a regression that drops the
  whole card is caught.

## Not covered by this plan

- **The pipeline itself (1.1–4.6, 6.3, 6.4, 7.1).** Discovery, ranking, audio
  extraction, transcription, the two LLM calls, the concurrency cap and the
  retry policy never cross the browser boundary. They are covered by the unit
  and workflow suites, which is where their feedback is cheap and deterministic.
- **A live end-to-end run.** Deliberately excluded from the automated loop for
  the reasons in *External calls* above. Worth one manual smoke run against a
  small account with `Reels = 1` before anyone relies on the output.
- **5.7 (`404` for an unknown run id).** Reachable only by requesting an API
  route directly, which is an HTTP assertion rather than a browser flow; it is
  covered in `app/api/runs/[runId]/route.test.ts` and was verified by hand
  against the running server.
- **7.4 (the README warning).** Documentation, asserted in `src/readme.test.ts`.

## Conflicts found between the spec and the code

1. **Port.** `design.md` and the loop's own instructions assume
   `http://localhost:3000`; the app and `playwright.config.ts` use **3001**.
   Tests must rely on `baseURL`, not a literal origin.
2. **Route layout.** `design.md` draws the UI under `src/app/`; the code has it
   at the repo-root `app/`. No effect on the tests — noted because it is an
   open item in `tasks.md`.
