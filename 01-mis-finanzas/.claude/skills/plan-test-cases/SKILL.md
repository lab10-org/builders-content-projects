# Plan test cases — the e2e plan of a spec

You turn a spec into **three executable-by-a-human test cases** and write them
to `docs/specs/<YYYY-MM-DD>-<feature>/e2e-tests-plan.md`. You do **not** write
Playwright code — that is the `generate-tests` subagent's job, and this file is
its only input. Write it so an agent that has never read the spec can implement
every step without guessing.

Normally you run inside the `verify-implementation` loop, which hands you the
spec folder. Invoked directly, resolve the folder the same way: the one the user
named, or the only spec under `docs/specs/`, otherwise ask.

## Step 1 — Read the spec, not your memory of it

1. `requirements.md` — the **EARS acceptance criteria** are the contract. Every
   case you write traces to one or more of them, by their exact identifier.
2. `design.md` — routes, page structure, component and field names, error
   copy, storage, external calls (e.g. an AI endpoint). This is where the steps
   and the expected UI text come from.
3. `tasks.md` — the Decision logs record where the implementation deliberately
   deviated from the design. A plan written against the design's *intent* when
   the code went another way produces false failures.

Then look at the actual UI code (`app/`, `src/components/`) for the routes,
labels, placeholders and button text the user would really see. Prefer what is
in the code over what the design says when they disagree, and note the
divergence in the plan.

## Step 2 — Choose the three cases

Exactly three, no more, no fewer:

1. **One happy path** — the feature's main flow, end to end, the way the user
   story describes it: navigate, fill, submit, and see the persisted result.
   Cover the criteria that define "the feature works"; if the flow has a
   meaningful post-condition (the item appears in a list, a total updates),
   assert it — don't stop at the success message.
2. **Two failure paths** — cases where the app must *refuse* or *degrade*
   correctly. Pick the two that carry the most risk, preferring criteria written
   as rejection or error behavior (invalid input, a boundary like zero or a
   negative amount, a missing required field, an unavailable external service
   with its fallback). Two variations of the same validation are one case, not
   two — pick two genuinely different failure modes.

A failure case asserts the **app's correct behavior under bad input**: the error
message shown, the submission blocked, nothing persisted. It is not a test that
is expected to fail.

## Step 3 — Write the plan

Write `e2e-tests-plan.md` (overwrite it if it exists — it is a derived artifact)
using exactly this structure:

```markdown
# E2E test plan — <feature>

Spec: `docs/specs/<date>-<feature>/`
Generated by `/plan-test-cases` · consumed by the `generate-tests` subagent

## Preconditions

- App: `npm run dev` on http://localhost:3000 (Playwright starts it automatically)
- Environment: <keys/env the flow needs, or "none">
- State: <what must be true before each case: cleared storage, a logged-in user, seeded data>

## Case 1 — <name> (happy path)

- **Traces to:** <criterion ids, verbatim from requirements.md>
- **Objective:** <what this proves about the feature, in one line>
- **Preconditions:** <case-specific state>
- **Steps:**
  1. <action, naming the real route/label/button: `/expenses`, the "Descripción" field…>
  2. …
- **Expected result:**
  - <observable assertion: visible text, element state, persisted value after reload>
- **Notes:** <flakiness risks, waits, external calls to intercept>

## Case 2 — <name> (failure path)
…same fields…

## Case 3 — <name> (failure path)
…same fields…

## Criteria coverage

| Criterion | Case | Covered as |
|---|---|---|
| <id> | 1 | happy path |

## Not covered by this plan

- <criteria left to unit tests or out of e2e reach, with the reason>
```

Rules for the steps and assertions:

- **Observable only.** Steps describe what a user does in the browser;
  assertions describe what a user can see. Never reach into internal state,
  storage or module functions — that is the unit suite's territory.
- **Concrete.** "Fill the amount field with `-50`" beats "enter an invalid
  amount". `generate-tests` must not have to invent data.
- **Name the surface.** Real route, real visible label, real button text, real
  expected error copy — quoted from the code.
- **Deterministic.** Avoid dependence on today's date, random data, or the order
  of the other cases; each case sets up its own state.
- **External calls.** If the flow hits an external API (the AI category
  suggestion), say explicitly whether the case exercises it live or expects the
  network to be intercepted, and what the fallback behavior must be.

## Step 4 — Hand off

Report: the file path, the three case names, which criteria are covered and
which are not, and any conflict you found between the spec and the code. Then
the caller continues the loop with `generate-tests`.

## Scope guardrails

- You write **only** `e2e-tests-plan.md`. Never touch `requirements.md`,
  `design.md`, `tasks.md`, `e2e/`, or any source file.
- Never invent a criterion the spec doesn't have. If a case you consider
  valuable has no criterion behind it, list it under "Not covered" with a note
  that the spec would need to change — that is `/specify`'s call, not yours.
- If the spec's criteria are too thin to yield three meaningful cases, write the
  ones that are real and say plainly which slot you could not fill and why.
