# E2E test plan — Sign in and sign up with Supabase Auth

Spec: `docs/specs/2026-07-30-login-supabase/`
Generated by `/plan-test-cases` · consumed by the `generate-tests` subagent

## Preconditions

- **App:** `npm run dev` on http://localhost:3000 (Playwright starts it
  automatically via `webServer`, `reuseExistingServer: true`).
- **Environment:** `.env.local` must hold `SUPABASE_URL=http://127.0.0.1:54321`
  and `SUPABASE_PUBLISHABLE_KEY` (the publishable key from `supabase status`).
  Without them every action throws before reaching the service — that is a
  blocked run, not a failing test.
- **External service:** the local Supabase stack must be up
  (`supabase status`; `curl http://127.0.0.1:54321/auth/v1/health` → 200).
  These cases hit **real** Supabase Auth — nothing is intercepted or stubbed.
  Auth is the feature under test; mocking it would verify nothing.
- **State:** each case starts from a fresh browser context (Playwright's
  default), so no session cookie carries over between cases. No `localStorage`
  seeding is needed or allowed — the app writes nothing there by design.
- **Seeded account:** `smoke-2026073001@example.com` / `s3cret-pass` already
  exists in `auth.users` of the local stack. Cases 2 and 3 depend on it. If it
  is missing, register it once through `/signup` before running them.

## Case 1 — Create an account from the sign-in screen (happy path)

- **Traces to:** 2.1, 2.2, 2.3, 2.4, 3.1, 3.2
- **Objective:** A brand-new visitor can go from the sign-in screen to an
  authenticated session in the app, with no confirmation step in between, and
  the session lives in cookies rather than in browser storage.
- **Preconditions:** Fresh context. The email used must not already exist, so
  the test generates a unique one at run time (see Notes).
- **Steps:**
  1. Navigate to `/login`.
  2. Click the link **"Create an account"** (it is an `<a href="/signup">`, not
     a button).
  3. Confirm the URL is `/signup` and the heading **"Create your account"** is
     visible.
  4. Fill the field labelled **"Email"** with the unique address, e.g.
     `e2e-signup-<timestamp>@example.com`.
  5. Fill the field labelled **"Password"** with `s3cret-pass`.
  6. Click the button **"Create account"**.
- **Expected result:**
  - The URL becomes `/onboarding/profile`.
  - No element with role `alert` is present at any point of the flow.
  - No text matching `/confirm/i` is shown — registration does not route
    through an email-confirmation step (2.4).
  - Reading `localStorage` and `sessionStorage` in the page returns **zero**
    keys: the session is carried by cookies only (3.2).
  - `document.cookie` contains `mis-finanzas:persist=1` but **no** cookie whose
    name starts with `sb-`: the session token is `httpOnly` and therefore
    invisible to scripts (3.1).
- **Notes:**
  - The address must be unique per run — derive it from `Date.now()`. Reusing a
    fixed one turns this case into Case 3 on the second execution.
  - Registration writes a real row to `auth.users` on the local stack. That is
    accepted: the rows are harmless and the alternative (deleting the user
    afterwards) would need the service-role key, which this feature keeps out of
    the tree entirely (5.3).
  - The submit is a Server Action round trip; wait for the URL, not for a
    timeout.

## Case 2 — Sign in with the wrong password (failure path)

- **Traces to:** 1.4, 1.5, 4.1, 4.7
- **Objective:** A rejected sign-in tells the user nothing about whether the
  email exists, keeps them on the form with what they typed, and never enters
  the app.
- **Preconditions:** Fresh context. The seeded account exists.
- **Steps:**
  1. Navigate to `/login`.
  2. Fill **"Email"** with `smoke-2026073001@example.com` (a real, existing
     account).
  3. Fill **"Password"** with `definitely-not-the-password`.
  4. Click the button **"Sign in"**.
- **Expected result:**
  - An element with role `alert` appears with the exact text
    **"Invalid email or password."** (4.1, 4.7) — the message names neither the
    email nor which half was wrong (1.4).
  - The URL is still `/login`.
  - The "Email" field still holds `smoke-2026073001@example.com` and the
    "Password" field still holds `definitely-not-the-password` (1.5).
  - `document.cookie` contains no cookie whose name starts with `sb-`: no
    session was established.
- **Notes:**
  - The assertion must be on the **exact** copy. A looser match would pass on
    the generic "Something went wrong. Please try again.", which is what this
    case exists to distinguish from a correct rejection.
  - This is the one case that proves the real SDK's `invalid_credentials` code
    reaches `mapAuthError`; the unit suite can only simulate that shape.

## Case 3 — Register an email that already has an account (failure path)

- **Traces to:** 2.7, 2.8, 4.2, 4.7
- **Objective:** A duplicate registration is refused with copy that sends the
  user to sign-in instead, without creating anything or losing what they typed.
- **Preconditions:** Fresh context. The seeded account exists.
- **Steps:**
  1. Navigate to `/signup`.
  2. Fill **"Email"** with `smoke-2026073001@example.com` (already registered).
  3. Fill **"Password"** with `another-pass`.
  4. Click the button **"Create account"**.
- **Expected result:**
  - An element with role `alert` appears with the exact text
    **"That email is already registered. Sign in instead."** (2.7, 4.2, 4.7).
  - The URL is still `/signup`.
  - Both fields still hold what was typed (2.8).
  - The link **"Sign in"** (`href="/login"`) is visible, so the way out the
    message names is actually there.
- **Notes:**
  - Supabase can answer this with either `user_already_exists` or
    `email_exists` depending on version and confirmation settings; both are
    mapped to the same copy, so the assertion holds either way.
  - Do **not** assert on how long the request takes: Supabase deliberately
    delays duplicate-signup responses as an enumeration defence.

## Not covered by this plan

- **1.1, 1.2 (a *successful* sign-in)** — no slot left: the plan allows one
  happy path, and Case 1 covers the fuller flow (sign-up establishes a session
  through the same server action and cookie machinery). A successful sign-in is
  exercised by `app/login/page.test.tsx` at the unit level.
- **1.3, 2.5, 2.6 (client-side validation)** — fully covered by the unit suites
  of the pages and `credentials.test.ts`, and they never reach the browser's
  network path, so an e2e run adds no information.
- **3.3, 3.4, 3.7 ("Remember me" and refresh persistence)** — the distinction is
  a cookie *attribute* (`maxAge` present or absent) and, for 3.7, requires an
  expired access token. Neither is observable to a user in a single browser
  session; `cookies.test.ts`, `serverClient.test.ts` and
  `middlewareClient.test.ts` assert them directly.
- **3.6, 3.8 (token refresh in the middleware)** — needs a token past its
  expiry, i.e. waiting out `jwt_expiry` (1 hour) or manipulating cookies. Out of
  reach of a deterministic e2e run.
- **4.3, 4.4, 4.5, 4.6 (weak password, rate limit, unreachable service, unknown
  error)** — each needs the auth service to be pushed into a specific state
  (config change, flooding, shutdown). Covered by `errors.test.ts`.
- **5.1, 5.2, 5.3 (configuration)** — a missing variable prevents the app from
  serving the flow at all; it surfaces as a blocked run, not as a test case.
